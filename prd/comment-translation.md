# 评论实时翻译

> **状态**：讨论稿，**v2 正式版之后**实现。
> 本文只定方案与边界，不含实现。

## 1. 问题

Gitalk 的评论区是**跨语言**的：一个中文博客会收到英文评论，一个波斯语读者看到的是中文讨论。
目前唯一的办法是复制出去、贴进翻译工具、再贴回来。

目标：**在评论下方实时把它翻成页面当前的语言**，且不把「读评论」变成需要付费或注册的功能。

## 2. 约束（这些决定了方案）

| 约束 | 含义 |
| --- | --- |
| **不能有服务器成本** | 项目的定位是纯技术影响力 ✓ —— 翻译必须落在**免费额度**内，或由使用者自己的 key 承担 |
| **组件可以被匿名读者使用** | 翻译不能要求登录 ✓ |
| **代理已经存在** | 两个平台（Cloudflare Workers / CloudBase）各有自己的免费额度 ✓ |
| **评论是别人的话** | 送到第三方翻译前必须**明示** ✓，并且**默认关闭** ✓ |
| **不能拖慢首屏** | 翻译是**按需**的 ✓，绝不预取全部评论 ✗ |

## 3. 候选方案

| 方案 | 免费额度 | 质量 | 额外依赖 | 评价 |
| --- | --- | --- | --- | --- |
| **Cloudflare Workers AI**（`m2m100-1.2b` / `nllb-200`） | **10,000 neurons/天** | 中等 | **无** —— 同一个 Worker 里调用 | ✅ **首选**：零新供应商、零新密钥、离线于浏览器之外 |
| **DeepL API Free** | 500,000 字符/月 | **最好**（尤其欧洲语言） | 需要 API key | ✅ **可选升级**：让用户填自己的 key，质量最好 |
| **LibreTranslate** | 自托管免费 | 偏弱 | 一个容器 | ⚠️ 只适合自托管用户 |
| **MyMemory** | ~1,000 词/天（匿名） | 弱 | 无 | ✗ 额度太小、质量不稳 |
| **Microsoft Translator F0** | 2,000,000 字符/月 | 好 | 需要 Azure 账号 | ⚠️ 要注册，增加门槛 |
| **浏览器端模型**（Transformers.js + NLLB） | 免费 | 中等 | **~600 MB 模型** | ✗ 与「37.5 kB」的定位冲突 |
| **Google Cloud Translation** | 无长期免费额度 | 好 | 需要结算账号 | ✗ 直接排除 |

**结论**：

- **Cloudflare 部署** → 用 **Workers AI**（同一份 Worker，不新增密钥）
- **CloudBase 部署** → Workers AI 不可用 ✗；**默认关闭**翻译 ✓，需要时让用户填 **DeepL** 或腾讯云机器翻译的 key ✓
- **自托管 Node** → 让用户选（DeepL / LibreTranslate / 自建）

## 4. 推荐架构

```
评论 ──[点击「翻译」]──▶ proxy /translate
                            │
                            ├─ 1. 查缓存（KV / CloudBase 数据库）
                            │      key = sha256(text + targetLang + engine)
                            │      命中 → 直接返回（0 成本）
                            │
                            ├─ 2. 未命中 → 调用引擎（Workers AI / DeepL）
                            │      并把结果写回缓存（TTL 30 天）
                            │
                            └─ 3. 返回译文 + 引擎标识
```

**要点**：

1. **只翻当前视口内、用户点了的评论** ✓ —— 不预取 ✗
2. **缓存是成本模型的核心** ✗ —— 一条热评被翻一次，所有人共享 ✓（TTL 30 天 ✓）
3. **按 (文本 + 目标语言 + 引擎) 缓存** ✓ —— 同一句话翻成不同语言分别缓存 ✓
4. **限流** ✓：按 IP 每小时 N 次 ✓（这里必须做 ✓，否则匿名读者可以刷光 neuron 额度 ✗）
5. **失败要优雅** ✓：引擎不可用时返回 `null` ✓，UI 显示「暂时无法翻译」✓，**不要**退回原文假装成功 ✗

## 5. 成本模型（估算）

Workers AI 的 `m2m100-1.2b` 按 neuron 计费 ✓，免费额度 **10,000/天** ✓。

- 一条 100 词的评论 ≈ 130 tokens ✓ → 单次翻译约 **1 neuron 量级** ✓
- 假设**缓存命中率 80%** ✓ → 每天可支撑约 **50,000 次点击** ✓
- 对一个技术博客的评论区，这个量级**远超实际需要** ✓

⚠️ 若某天超额 ✗：当天翻译功能自动降级为「不可用」✓，**不影响评论本身** ✓ ✓（翻译是增量功能 ✓，不是核心链路 ✓）。

## 6. 隐私与合规

评论正文是**用户的内容** ✓，送到第三方（Cloudflare / DeepL）意味着**离开我们的基础设施** ✗：

- **默认关闭** ✓ —— 由站点主在 `options.translation.enabled` 里显式开启 ✓
- **首次使用时明示** ✓：「评论将被发送到 <引擎> 进行翻译」✓ 并提供一个「不再提示」✓
- **不做批量预翻译** ✓ —— 只有读者主动点击的那一条会离开 ✓
- **不缓存原文** ✓ —— 缓存只存 `hash → 译文` ✓，原文不留 ✓
- **可关闭** ✓：`translation: false` 时请求根本不发 ✓

## 7. UX

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| **触发方式** | 每条评论一个「翻译」按钮 ✓ | 自动翻译会让页面在滚动时不断发请求 ✗，且读者并不总是需要 |
| **显示方式** | 译文**展开在原文下方**（保留原文 ✓） | 译文可能错 ✓ —— 原文是权威 ✓ |
| **语言** | 默认翻成**页面当前语言** ✓，可切换 ✓ | 与落地页的语言下拉一致 ✓ |
| **标记** | 明确标注「机器翻译」✓ + 引擎名 ✓ | 不让人误以为作者用那种语言写的 |
| **RTL** | 译文按**目标语言**的方向渲染 ✓ | 中文评论翻成波斯语时，译文块要 `dir="rtl"` ✓ |

## 8. 数据契约（草案）

```ts
interface TranslationRequest {
  text: string          // 上限 ~5000 字符，超出直接拒绝
  target: string        // BCP-47，如 'zh-CN'
  source?: string       // 省略则自动检测
}

interface TranslationResult {
  text: string
  source: string        // 检测到的源语言
  engine: 'workers-ai' | 'deepl' | 'libretranslate'
  cached: boolean
}
```

## 9. 实现顺序（v2 正式版之后）

1. **代理加 `/translate`** ✓ + KV 缓存 ✓ + 按 IP 限流 ✓（Workers AI）
2. **组件加「翻译」按钮** ✓ + 译文块 ✓ + 方向处理 ✓
3. **DeepL 引擎** ✓（`options.translation.engine: 'deepl'` + 用户 key）
4. **CloudBase 的支持** ✓（或明确「此平台暂不支持翻译」✓，不要静默失败 ✗）
5. **落地页补一句说明** ✓（翻译是可选能力 ✓，需要开启 ✓）

## 10. 明确不做

- ✗ 不做**自动**翻译（成本不可控 + 隐私面变大）
- ✗ 不做**翻译后写回 GitHub**（评论区的数据以仓库为准 ✓，不在中间层留副本）
- ✗ 不做**社区词表**/术语定制（v3 再说 ✓）
- ✗ 不承诺质量 —— 一律标注「机器翻译」✓
